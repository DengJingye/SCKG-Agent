# 原预算内一次最终格式修复

新提交的开发态流程对话显式绑定 `answer_contract_version=report_presence_v4` 与 `repair_policy=final_format_once_v1`。它复用现有 agent 循环、ModelService、Ledger 和执行者检查；没有新增任务队列或更换模型接口。旧请求没有该 policy 时保持原行为，历史失败不会被重新生成或改成成功。

## 触发范围

必须已经成功执行本轮只读输入检查。失败输出须为严格 JSON 对象，明确声明 `action=finish`、空 `route_ids/reports` 和完整 answer 对象；其原始输出、实际请求、完整格式、模型配置及失败回执必须重新绑定。仅支持能安全定位的结构错误，例如摘要超过原长度限制。

解析失败、再次 evaluate、结果或用量未知、超时、返回模型身份变化、来源变化、取消和预算不足均停止。已经通过网关格式检查、随后被来源或输入状态验证拒绝的回答不进入该修复策略。字段长度、P/E 引用及 V4 输入状态规则保持不变。

## 调用与记录

正常路径为检查、工具结果、最终回答。若第二次请求得到符合上述条件的非法最终输出，应用可在同一个三次请求总上限内，再生成一次完整最终回答；没有第四次请求，也不重新执行工具。该过程是应用显式重生成，SDK 重试仍为零。

`workflow_run` 使用独立版本 `development-workflow-chat-format-repair-v1`：`attempts` 保留全部真实请求，包括格式失败；`calls` 仅保留被接受的动作。失败请求没有伪造的成功动作。重放逐一核对连续序号、唯一 call ID、原始响应和预算；删掉失败尝试并重算外层哈希仍会使回答失效。

修复预留与执行者身份、预留不存在检查在同一个 `BEGIN IMMEDIATE` 事务中完成。已有预留不能再次消费；结果未知时沿用现有核对路径，不自动重发。这里保证的是应用修复机会有界，不是远端 API 的 exactly-once 执行保证。

发送给模型的是原有完整上下文及至多 1024 字节的安全诊断对象，包含静态字段路径、校验器、长度与绑定哈希。坏回答正文、任意属性名及校验异常原文不进入新请求。完整最终 payload 在调用前重新做容量检查，不能截去来源条件或扩大预算。

实际已知的失败用量照常计入总量；未知用量保守预留并停止。输入 UTF-8 字节代理、输出预留与 provider 报告 tokens 分别记录。金额未知仅在原请求明确允许、且没有金额上限时继续按 token/调用限制控制；不能写作零费用。
