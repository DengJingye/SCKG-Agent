# 流程对话的阶段合同

`phase_bound_v3` 将“先读取工具检查，再回答”写入实际发送和本地验证的完整 JSON Schema。它复用既有 ChatService、ModelService、有界循环和只读输入检查，没有增加 agent 角色、模型请求上限或科学执行权限。

| 阶段 | 允许动作 | 关联字段 |
| --- | --- | --- |
| 首次输入检查 | `evaluate_workflow_inputs` | 1–4条不重复路线，0–8项原话报告；`answer=null` |
| 工具返回后 | 再检查，或 `finish` | 再检查仍须空answer；结束必须空routes/reports及完整回答对象 |
| 第三次模型请求 | 只能 `finish` | 空routes/reports及完整回答；不能继续检查 |

中间阶段使用按 action 区分的互斥分支。E引用、原用户原话、P状态、missing规则、来源身份和工具预算继续逐项验证；阶段合同不会把候选升级为可信推荐，或证明科学适用性。

研究台启用开发流程对话后，新表单会绑定V3；输出接口仍由用户显式选择JSON Schema或JSON对象，不自动切换。程序调用可在原`workflow_options`中增加`answer_contract_version="phase_bound_v3"`。未指定版本的旧API调用继续使用V2；已保存的V1/V2轮次按原版本重放。新请求的版本选项与准备结果不一致时拒绝，不能通过None或V2覆盖降级。

## 实际验收

主工作区新增32项阶段测试与原32项接口测试通过，另464项相关回归通过；两通道串行运行，每通道120秒/1.5GiB。历史V2四份格式快照来自已封存协议，测试逐项比较；V1/V2提示和格式不追改。

公开副本64项合同测试通过；原464项整组触及120秒上限，失败原件保留。随后在同一源码快照上串行完成232＋232项，两片均无失败或跳过，JUnit并集精确等于原464项且没有重复；各片仍限120秒/1.5GiB。

实际旧失败输出还用于零调用隔离检查：仅把长candidate ID替换为语法合法E编号后，旧V2 schema可接受，但V3初始schema仍因非空answer拒绝。该派生对象是工程反例，不是新模型输出或真实证据引用。

新的独立W02协议保留原问题、21条来源候选、M0及资源上限。实际完整交互用2次模型请求、1次只读检查完成，27.59秒，采样父子进程峰值112.5MiB，报告13,885 tokens，金额未知。原话、工具结果、实际请求和最终回答绑定；只读收集及保存轮次重放通过，未追加请求。剩余一次额度关闭；未拟合分析、修改生产库或重写旧失败。

完整工作台12项界面检查通过：一份独立副本显示实际成功回答、三条未知输入报告、来源及两次回执，两次刷新不写入或重发；另一份独立副本通过原提交接口登记一条待处理请求，确认V3、显式JSON对象及预算均持久保存，仅在后台launch边界阻止执行。后者是提交接线夹具，没有制造模型响应，也不计为第二次真实交互。

这是一个真实单例的工程完成，不能据此计算可靠性提升百分比、知识增益或外部agent排名。仍有机制性语义缺口：当前unknown_requirements把未报告与已报告null合流，finish规则要求not_supplied，因此真实回答的分类也受服务端规则影响。后续应复用已有报告、P、原话/span及回执区分“没有报告”与“已有原话、有效性未知”，版本化调整理由和追问规则；不能只改模型措辞。当前输出与V3历史重放保留，不事后润色为满分。后续继续多场景交互、知识消融及原生外部比较。
