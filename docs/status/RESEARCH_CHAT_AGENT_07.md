# 07 — Research Chat Scientific Agent

Worktree: `SCKG-Agent-candidate-demo`, branch `feature/candidate-kg-demo-v1`.
Date: 2026-09-20. This document describes product changes; it does not promote scientific knowledge.

## Confirmed root causes

1. The active Streamlit process was running this worktree. It had neither its own `.env` nor an encrypted API configuration. `Settings` intentionally loads the current project configuration, not an unrelated worktree's credentials. The existing configured provider was found in the main `SCKG-Agent` worktree: `api.deepseek.com`, model identity `deepseek-v4-pro`. Only configuration identity and credential presence were inspected; model keys were not printed or copied.
2. The UI's per-session external-model consent defaulted to false. Saving credentials, having environment credentials, and authorizing outbound questions are separate states.
3. The existing semantic parser already proposed read-only tools, but scientific synthesis received neither dialogue history nor the current study context. Conversation state remembered tasks/tools but lost relevant study conditions.
4. `external_answer_preserves_bindings` required exact evidence sentences plus their exact citation strings. Natural Chinese paraphrases fell back to deterministic reports. Generic caveat follow-ups were also forced through the default Top-3 formatting check.
5. The UI intercepted greetings and returned a capability/governance explanation. It also resolved an old data binding and called `st.stop()` before determining whether the new question depended on that data.
6. KG retrieval diagnostics contained useful statement/scope/requirement paths, but those paths did not become the synthesis contract or the user's answer-to-source experience. The default corpus also differed from the existing qualified frozen retrieval snapshot.

## Current architecture

```text
explicit configuration + outbound consent
  -> deterministic safety precheck
  -> semantic intent, task, current study context, read-only tool proposals
  -> bounded registry execution (catalog / evidence / contracts / capability discovery)
  -> fresh claim bindings + exact Scientific KG mappings
  -> bounded response context + recent dialogue + latest request
  -> natural structured synthesis
  -> exact quote/citation validation
  -> bounded same-model source entailment check / narrowing
  -> deterministic type, numeric, method-scope and execution-claim audit
  -> decision-local answer / citation popovers / Why and Evidence panels
```

The entailment check is a fallible same-model assessment. It is **not independent semantic verification**, human review, evidence promotion, or permission to execute. The UI says so. A failed individual claim can be removed without replacing all useful answer content with an FAQ. Plain prose from a provider that disregards JSON mode is recovered only through the same source/entailment/audit checks; malformed structured answers and invented citation indexes are rejected. If the model miscopies a quote attached to a valid index, its quote is discarded and the server's registered excerpt is used for the subsequent entailment check. This is recorded in `quotes_resolved_from_store`; invented text never becomes an EvidenceSpan.

ASK is generated by the model when authorized and available. PLAN continues to compile existing capabilities or describe an existing generic recipe; RUN continues through existing data grants, plan approval, contracts, compiler and execution guards. Neither the synthesis JSON nor conversation state grants execution authority. Generic plan modification is distinct from inspecting an unbound dataset.

### Context and evidence contract

- Eight bounded conversational turns; previous assistant prose is context, never scientific authority.
- User-reported slots retain an exact user-quote provenance. They do not assert measured matrix state, file availability, or biological results.
- Current semantic question and fresh search observations are regenerated on follow-ups.
- Up to eight source references and twelve KG statement paths; candidate/requirement/scope information enters synthesis before answer generation.
- Server-resolved Statement → Assessment → EvidenceSpan → SourceRevision links, locators, exact indexed excerpts and registered source URLs.
- Explicit `KG_GROUNDED`, `RETRIEVAL_GROUNDED`, and `MODEL_KNOWLEDGE` distinctions. The graph's candidate status is retained.
- The visible evidence projection includes only references cited in the answer. Retrieved but unused sources do not count as KG gain.
- No model-supplied evidence IDs, scores or trust flags can promote knowledge.

### Data and runtime behavior

An inaccessible historical binding is a warning for unrelated ASK, a rebind/inspection request for data-dependent questions, and a blocker for RUN. User descriptions never substitute for an authorized profiler or ledger. Per-request model enablement no longer mutates process-wide privacy settings in the UI.

The launcher's `--enable-external` is explicit local-server authorization for sanitized Chat context; merely finding a key never enables outbound calls. Runtime status separates configured/enabled from an answer actually generated by the model. Model failures are visible as local fallback.

## Frozen knowledge limitation

The existing Scrublet KG input statement resolves to a verified candidate binding, but its `uat-authoritative-span:scrublet.input_output` is absent from the frozen indexed corpus. The adapter correctly reports `GRAPH_EVIDENCE_NOT_IN_CORPUS`. This change preserves that gate and does not silently inject or promote the span. Doublet conversations can use existing paper/README retrieval evidence, while the UI honestly reports when no direct KG statement supported the answer.

Scanpy HVG's conditional input statement is available in the qualified corpus and supports the complete chain, including version/flavor scope. It remains candidate knowledge. This demonstrates a working KG path; it does not prove that the KG improves every method-selection decision or outperforms RAG.
